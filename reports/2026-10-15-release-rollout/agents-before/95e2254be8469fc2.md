## FlexLock migration and neural-field workflow (2026-10-14)

FlexLock 0.9.2 is installed in the previously shared MaxSS environments. Both
main and neural-field manifests/locks pin the reviewed local wheel. The
neural-field manifest's tcwind_benchtools and zarrpatch paths are now absolute
references to the same shared packages used by its existing launch convention.
The worktree's standalone environment has not been installed by this migration.

Preserve the existing launch convention when using the shared environment:
activate the main hpc environment, put the neural-field src first on PYTHONPATH,
and execute from /scale/user/qfebvre/projects/250930_maxss_era5pp. Existing
results_hafs and validation-panel paths are relative to that experiment root.
Check actual FlexLock and scientific module import paths before submitting.

Compatibility changes:

- Destination/queue ownership is checked before scheduler submission. Use a fresh
  absolute save_dir set before config resolution. --force cannot bypass active
  queue ownership. Preserve completed checkpoints, panels and run records.
- Concrete run_lock references bind selected producer records before submission;
  changed/missing producers cause failure. --after keeps the exact future path.
- Output contracts and authoritative records gate successful reuse; submission
  does not imply scientific completion. Inspect task rows and stage receipts.
- Fresh nested outputs may omit .flexlock-queue.json. Use shared FlexLock record
  readers; consumers of queue layout 2 need 0.9.1+. Keep pending outputs with
  their ancestor queue; audit dependencies before moving historical artifacts.
- Python configs, py2cfg, @ presets and sweeps remain supported. Cache/pipeline
  retirement is still pending; this deployment does not remove their old APIs.
- FlexLock no longer depends on pandas; scientific and optional MLflow packages
  retain their own requirements.

Validation checked installed readers and the actual neural-field cfg_smoke source,
callable signature, and logger/checkpoint paths after a fresh save_dir override.
Completed-run artifacts were hashed and remained unchanged. Training and inference
were not replayed. Dirty/untracked scientific files were preserved and not committed.

For new organization, begin with one imported arm config, explicit retained input
bindings and a fresh track/arm/run directory. An arm label does not select an
architecture by itself. Keep legacy launch modules and result paths during the
pilot. Review data, checkpoint and cached-panel compatibility before any new run.

The guidelines are maintained centrally; keep concrete project choices and exceptions here.
Research, knowledge and reporting instructions elsewhere in this file continue to apply.

- Use a fresh absolute run destination; track/arm/run is a useful naming convention,
  not a required schema or an automatic architecture selector.
- Select concrete upstream runs in configuration. Keep data snapshots tied to effective
  callable input arguments, and producer lineage tied to the corresponding selection.
  Preserve direct run_lock interpolation, overrides and sweep-file usage.
- Freeze file-list campaign membership. Check accepted outcomes for every expected item
  before aggregation; queue completion alone does not establish scientific coverage.
- Keep resource profiles separate from scientific choices. For different stage resources,
  use a small orchestration script with --after and persisted accepted job IDs. A reporting
  failure after submission must not cause blind resubmission.
- Retain original locks and artifacts. Before archiving config entrypoints, audit callers;
  before moving outputs, audit upstream references and active queue ownership.

Project starting point: Start with one Python config entrypoint and explicit retained-input bindings. Add separate stage or track modules only when actual reuse warrants them. Keep existing scientific parameters, split definitions and artifact paths during the first bounded comparison. Keep the main-hpc/worktree-src launch convention documented above and its experiment-root working directory. Import the selected arm config explicitly; logger/checkpoint paths must follow the fresh save_dir. Preserve validation panels and completed models.

This section guides new work; it does not assert that all historical workflows have
been replayed or that production configs/artifacts have been reorganized. Record actual
entrypoints, selected artifact paths and validation outcomes here when a project adopts
its first recipe; do not infer missing historical provenance.

## FlexLock adoption — adopted recipe (2026-10-14, submitted for review)

First project-owned workflow on the 0.9.2 recipe (evidence: neural-field worktree
`reports/flexlock-adoption/report.md`): I39 latent flow matching.

- Config: `maxss_configs.workflows.nf_latent_fm` (`cfg`, `cfg_smoke`); stage wrappers
  `maxss_diff.nf_latent_fm_workflow`; acceptance helpers `maxss_diff.flexlock_bindings`
  (`require_product` for declared outputs, `require_legacy_file` for pre-adoption records whose relative
  save_dir resolves against the experiment root).
- Destinations: `results_hafs/runs/<track>/<arm>/<run>/<stage>/` (absolute `runs_root`); every product
  inside its stage dir; producers chosen by root anchors (`base_run`, `collect_run`, `embed_run`,
  `training_run`) and read with `${run_lock:...}`. No cache search (default `raise`; a reused label fails).
- Commands (experiment root, main hpc env, worktree src first on PYTHONPATH):
  `flexlock-run -d maxss_configs.workflows.nf_latent_fm.cfg_smoke -s collect embed train evaluate -o run=<label>`;
  Slurm chain `python maxss-ml/.claude/worktrees/neural-field/scripts/orchestrate_nf_latent_fm.py --run <label> [--dry-run]`
  (`--print-job-id` + `--after`, ledger under `results_hafs/runs/ledgers/`; on partial failure relaunch only
  missing stages with `--stages`); frozen reassessment `-s evaluate -o run=<new> collect_run=... embed_run=... training_run=...`.
- New multi-stage work should copy this pattern. Legacy `results_hafs/<slug>_NNNN` configs and their results
  stay as they are until their track is migrated (deferred callers listed in the report).
